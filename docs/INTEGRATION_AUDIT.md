# Portal integration audit and sync health

The scope sheet's P0 Platform row calls for an audit log plus integration sync health and failures. This implementation establishes the portable PostgreSQL `portal_integration_runs` table and an Audit Log at `/internal/audit` (also available as `GET /api/internal/audit`) for Internal Access Managers and Internal Admins. It is separate from the existing `portal_internal_access_audit` account and panel-activity table. Both are shown in the read-only view; the browser has no database credentials.

## Current coverage

- A connected internal user's live Hubstaff dashboard load records a `running` row before the provider read, then `succeeded`, `partial`, or `failed` after it completes. The row includes source, operation, environment, request trigger and UUID, initiating portal user ID, times, task-plus-project record count, and the number and outcome of 401-triggered renewals. A bounded/truncated provider result is `partial`, not a full success. Fields for records written/skipped/failed, connector version, and source window are present for later connectors; they remain zero/null for this read-only request. Failures store only a controlled error code, never provider messages, URLs, task contents, passwords, or tokens.
- Account creation, account updates, role grants/revocations, manager password resets, and terminal role changes continue to use `portal_internal_access_audit`. Terminal events have no portal actor ID; the terminal operator is not yet identified in that table.
- `platform.audit.read` is granted to `internal_access_manager` and `internal_admin`. Ordinary HR, Leadership, developer, and other business roles cannot read the log. The API enforces this even when opened directly. Integration runs and portal activity paginate independently, 20 rows per page, with Older/Newer controls. A fixed snapshot keeps newly written audit entries from shifting the pages while browsing; Show latest entries starts a fresh view. The rows remain in PostgreSQL; the page size is not a retention policy.
- Hubstaff does not provide an authoritative source timestamp for this dashboard response, so `source_timestamp` remains null. A null is preferable to presenting portal completion time as the source's update time. A read-through cache now creates an integration run only when it actually calls Hubstaff. The Team directory records a `team_directory` run with actor, outcome, and AOC member count; a cache hit creates no provider run. Every successful server response for a live internal panel writes `panel.read.<panel_id>` for each enabled panel, including cache hits. Authorized functional-role page opens write `role.view.<role_id>`. Internal Settings and Audit Log reads have their own controlled actions. No audit record stores leave reasons, balances, task contents, tokens, or raw provider payloads.
- The Internal Settings connection overview records `integration_settings.read`. An Internal Admin's manual Hubstaff connection test records a `hubstaff / connection_test` integration run with actor, outcome, safe error code, and member count only. A failed or missing audit migration prevents the test; the test never returns Hubstaff member names or credentials to the browser.
- A personal Hubstaff OAuth connection attempt records a `hubstaff / oauth_connection` integration run and a successful `hubstaff.oauth.connect` access action after the approved identity is verified and encrypted credentials are stored. Failed attempts retain only a controlled error code. The OAuth callback never records the authorization code, access/refresh tokens, or provider response body.
- Unlinking a personal Hubstaff connection records `hubstaff.connection.unlink` in `portal_internal_access_audit` in the same database statement that clears the saved credentials. It does not create an integration run because it makes no provider request.

## Standard for every new role and panel

Register a new live panel in `INTERNAL_USER_PANELS` and its server-side permission policy, then write a controlled audit event for successful reads and for each meaningful mutation. Register role workspace views with the shared role-view audit helper. Use `portal_integration_runs` only for actual provider reads or sync attempts, not cache hits; use `portal_internal_access_audit` for who accessed which panel or changed portal state. Record actor, action, target where applicable, and time, but no business-record contents. Test authorized and denied direct API calls, cache-hit reads, failures, and redaction before enabling the panel. Static Phase 0 placeholders have role-view events but no business-data read events.

## Deployment

After the existing portal and internal-user migrations, verify the intended database and run `npm run integration-audit:migrate -- --dry-run`, then `npm run integration-audit:migrate` against that same environment. Do not test the migration on production first. The migration uses standard PostgreSQL SQL and is portable to Neon or Supabase PostgreSQL. Deploy the code only after the audit migration; a connected Hubstaff dashboard load requires the table to start its run record.

## Remaining scope from the sheet

The sync interval is an on-demand freshness limit in whole minutes, not a scheduled job. Internal Admin can change it in Internal Settings; Access Managers can view it. Changes are recorded in `portal_internal_sync_settings_audit`. Shared snapshots retain normalized portal responses in PostgreSQL, never provider tokens as row keys. Expired snapshots are pruned after seven days when a successful refresh occurs. This cleanup is not guaranteed to run if nobody opens a workspace. Before production, approve HR cache retention and a periodic purge process.

There is no scheduled background sync worker in the current portal. Future Hubstaff Time/Tasks, HubSpot, Help Scout, Drive, and other connector jobs must use this run lifecycle, including source timestamps when the provider supplies them, records processed, retries, and sanitized failure codes. Before enabling write-back, add action-specific audit records with actor, target, outcome, and recovery correlation; do not treat integration-run records as a substitute for write-action audits. Detailed HR retention and per-record access-audit policy still need data-owner approval; current audit is panel-level, not per employee record. Permission-aware AOC-GPT requests/actions need their own approved audit policy. Set a retention and archival policy before production volume grows, especially now that ordinary panel reads create audit rows. Self-service password changes through Better Auth are not yet atomically coupled to the portal audit table; treat that as a remaining action-audit gap before calling the audit coverage complete. Decide whether Leadership or developers should receive a dedicated, narrower operational-read permission.
