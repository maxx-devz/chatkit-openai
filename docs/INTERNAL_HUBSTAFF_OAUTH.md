# Internal user Hubstaff connection (OAuth)

The portal's own username/password login remains unchanged. **Connect with Hubstaff** links an already signed-in internal user's approved Hubstaff identity to their personal **My Work** data. It is not portal SSO. This first version requests only `hubstaff:read` and `tasks:read`; it does not grant or implement write actions. The existing manual personal access token (PAT) form remains as a fallback. Team/HR organization reads and the shared Project Management connector use their separate server credentials.

## Set up the Hubstaff application

1. In the Hubstaff developer application, enable the authorization-code flow and register the exact callback URL for each portal environment: `https://YOUR-PORTAL-HOST/api/internal/hubstaff/oauth/callback`. For local development, use `http://localhost:3000/api/internal/hubstaff/oauth/callback` when `BETTER_AUTH_URL` is `http://localhost:3000`, and start Next.js on `localhost`. Do not mix `localhost` and `127.0.0.1`.
2. The portal requests only `hubstaff:read` and `tasks:read` when it sends a user to Hubstaff. Do not add write scopes until approved write actions, authorization, and audit behavior are implemented.
3. Set these **server-only** variables in `.env.local` and separately in the intended Vercel environment: `HUBSTAFF_OAUTH_CLIENT_ID`, `HUBSTAFF_OAUTH_CLIENT_SECRET`, and `HUBSTAFF_OAUTH_REDIRECT_URI`. The redirect URI must have the same origin as `BETTER_AUTH_URL` and end at the exact callback path. Keep the existing `HUBSTAFF_TOKEN_ENCRYPTION_KEY`; changing it can invalidate existing connections. Never place client secrets, tokens, or connection strings in source, chat, or browser code.
4. Confirm the target database, then run `npm run internal-hubstaff-oauth:migrate -- --dry-run` and `npm run internal-hubstaff-oauth:migrate` against that environment **before deploying the new code**. The migration adds `hubstaff_connection_kind`, defaulting existing connections to `pat`. It uses standard PostgreSQL SQL and does not replace portal accounts or Hubstaff mappings.
5. Deploy/restart the app. Sign in with an internal account that has the Hubstaff panel and connection permission, then open **Settings → Hubstaff → Connect with Hubstaff** (or **Reconnect with Hubstaff sign-in** if already connected). Approve the read-only request on Hubstaff. The callback verifies that the Hubstaff identity matches the portal account's approved mapping and that the account/session/mapping did not change during sign-in. A cancelled or failed attempt leaves the previous connection intact. Test a normal return, cancellation, wrong account, and reconnect. Check the Audit Log for a sanitized `hubstaff / oauth_connection` run and a successful `hubstaff.oauth.connect` access action.

The portal stores the returned access and rotating refresh tokens encrypted. Its callback state is encrypted, bound to the current portal session and mapping, and expires after ten minutes. OAuth tokens refresh through the Hubstaff application; legacy PAT tokens continue through the PAT path. A later write release will need a separate scope change and user re-consent, plus action-specific permission and audit tests.

An internal user with an active personal connection can open **Settings → Hubstaff → Unlink Hubstaff**. This removes the portal's saved personal access and refresh tokens, resets connection/sync state, and records `hubstaff.connection.unlink` in the access audit. It leaves the portal account, approved Hubstaff user mapping, and organization-level Team/HR connector untouched. It does not revoke an OAuth app grant or PAT within Hubstaff itself. The user's My Work data stops loading until they reconnect; an already-open browser tab may still show data it loaded earlier until refreshed.

When an authorized internal user has no saved personal connection, **My Work** shows a Connect Hubstaff button. It starts OAuth sign-in directly when the app is configured; otherwise it opens the Hubstaff setup in Settings, where the personal-token fallback remains available. The button is hidden after a connection is saved and never appears for accounts without the Hubstaff panel.

Before a personal connection is saved, My Work shows only this connection prompt; task, time, activity, and daily-plan panels stay hidden. Team and other authorized workspaces remain available because they use separate permissions and organization-level data access. If the Hubstaff panel is disabled, My Work instead shows a request-access message.

The portal allows `https://account.hubstaff.com` as the only external form-navigation destination so browsers can follow the same-origin connection POST's redirect to Hubstaff. Other portal form destinations remain limited to the portal origin.

No live migration or Hubstaff application configuration is performed by this document. Verify the real provider flow in the target environment before declaring it ready.
