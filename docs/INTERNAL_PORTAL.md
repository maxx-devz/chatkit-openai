# Internal Portal prototype

The Internal Portal has My Work, Team, personal Settings, read-only HR and Project Management workspaces under **My Workspace**, other functional-role placeholders, and role-gated Internal Settings. **My Work** lives at `/internal`, the shared **Team** directory at `/internal/team`, personal **Settings** at `/internal/settings`, and My Workspace panels at `/internal/roles/{role}`. **Internal Settings** has sidebar children for Users & Access (`/internal/internal-settings`), Integrations (`/internal/internal-settings/integrations`), and Sync (`/internal/internal-settings/sync`); Audit Log remains separate. Better Auth remains the shared login system.

My Work contains the internal user's own Overview, My tasks, daily plan, and Activity panels. Team contains the directory of active members of the configured AOC Hubstaff team, including those without portal accounts; shared project tasks live in Project Management, not the Team page. Settings contains separate Account Settings and Hubstaff panels. Both are enabled by default and independently toggleable. The sidebar switches between these containers with normal portal navigation; personal and team information are never mixed into one long dashboard. The internal user layout remains mounted during those client-side transitions, and each workspace response is kept in a per-session browser memory cache so returning to a loaded workspace does not show another loading pass or call the dashboard endpoint again. The sticky shared header exposes the explicit **Refresh Hubstaff data** action in every workspace. Team and personal work require their corresponding assigned panels and permissions; changing a password requires the Account Settings panel and `account.password.change`.

## Access architecture

Existing client authorization remains in `portal_memberships`; AOC staff authorization remains in `portal_admins`. The `portal_internal_users` table links to `portal_users` and contains the fixed `internal_user` account category, job position, explicit panel-access policy, active flag, approved Hubstaff user ID, encrypted access and rotating refresh tokens, access expiry, connection version, and synchronization/rate-limit timestamps. The account category is not a business role: department roles and capabilities will be modeled separately. The migration renames the legacy `portal_employees` table and its `role` column in place, normalizes that fixed value to `internal_user`, and preserves user IDs, authentication records, sessions, Hubstaff mappings, and encrypted tokens.

The position presets include **Team Member**, **Project Manager**, **Account Manager**, and **HR Admin**. They receive the same personal and Team panels by default; Project Manager also defaults to the PM project and task panels. A position does not grant the Project Management role. An Internal Access Manager or Internal Admin can toggle Team or other panels after applying a preset. The server checks active-account, panel, and permission access before returning Team, personal work, or connection data. The baseline `people.directory.read` permission does not bypass a disabled Team panel.

The [Internal Portal Role and Permission Matrix](INTERNAL_ACCESS_MATRIX.md) separates account type, position, functional roles, and exact permissions. Phase 0 allows assigning business roles. HR unlocks a read-only AOC-team-scoped reader for leave requests/calendar, balances, people, and schedule coverage. Project Management unlocks a read-only Hubstaff Tasks project catalog and per-project task list. Other business integrations remain placeholders. Personal self-service, Team, Internal Admin, and Internal Access Manager grants remain live.

The [Navigation Page and Panel Matrix](PORTAL_NAVIGATION_PAGE_PANEL_MATRIX.md) records which links, panels, and actions are live, and which business-role areas remain placeholders. It is updated as a page or field gains an approved source, scope, and permission.

The HR workspace at `/internal/roles/hr` reads only from the server-side Hubstaff organization token through `GET /api/internal/hr?month=YYYY-MM`. The API requires the HR functional role or Internal Admin, plus explicit leave, balance, schedule, availability, and capacity permissions. The HR Admin position alone does not grant those records. Internal Admin inherits every currently live Internal Portal permission, including detailed HR reads; personal Hubstaff work remains self-only. Results are limited to active AOC team members, audited, and marked private/no-store. Leave approval, balance changes, and schedule changes remain in Hubstaff. Review existing HR and Internal Admin role holders and the deployment's source coverage before release.

The Project Management workspace at `/internal/roles/project_management` reads folders, active projects, and member names from the shared Hubstaff Tasks organization via the server-side `HUBSTAFF_PAT_REFRESH_TOKEN`. Selecting a project loads its tasks; the UI displays title, stage, status, assignees, and due date, but not descriptions, comments, or provider credentials. `GET /api/internal/project-management` requires the Project Management role or Internal Admin, `work.projects.read`, and an enabled PM panel; `project_id` additionally requires `work.team_tasks.read` and the PM task panel. The server verifies the selected project belongs to the catalog before loading tasks. Access and provider runs are audited, responses are private/no-store, and PostgreSQL snapshots use separate project-catalog and project-task intervals. All PMs see the same accessible organization projects rather than individual assignments. This is a provisional shared-scope foundation: verify that the PAT sees the full intended AOC Tasks organization before production use, and set `HUBSTAFF_TASKS_ORGANIZATION_ID` if the PAT sees more than one organization. Time reports, workload calculations, task editing, and task assignment remain deferred.

The [Integration Audit](INTEGRATION_AUDIT.md) documents the Phase 0 operational run log, its restricted reader, migration, and remaining connector coverage. A live internal Hubstaff dashboard read now records success or a sanitized failure; the existing access-change audit remains a separate table.

Each business functional role has a panel under `/internal/roles/{role}`. Only an active user assigned that role, or an Internal Admin, can open it. HR and Project Management are live read-only workspaces; other business role panels remain static Phase 0 placeholders. Internal Access Manager uses the existing Internal Settings page instead of a business panel. Each available role links directly from the sidebar; on mobile, a hamburger button opens that same sidebar as a drawer. The old `/internal/roles` index redirects to the first available role panel.

Client and admin data-access guards reject accounts with an internal user record, including inactive internal users and accidental overlapping memberships. This protects client APIs, ChatKit, assistant settings, client Hubstaff reads, client library, and administrator operations at their existing shared authorization boundaries. Internal user endpoints independently verify the Better Auth session and active internal user record on every request. Existing client/admin accounts keep their access when no internal user table has been installed.

Provision internal users as **new, distinct accounts**. The creation command refuses existing usernames and Hubstaff mappings. Do not assign internal user records to existing client/admin accounts: internal user exclusion intentionally takes priority. Disabling an internal user should keep its internal user record, set `is_active` to false, clear its encrypted token, and increment `connection_version`; deleting the record could re-enable an accidentally retained legacy membership.

## Internal Settings access controls

An **Internal Admin** can see and access every currently live Internal Portal panel and workspace, including detailed HR and read-only Project Management records, and has all Internal Access Manager account-management permissions in Internal Settings, including editing their own account details except protected status and roles. Personal Hubstaff tasks, activity, and connection remain tied to that admin's own account. Internal Admin cannot change their own roles through Internal Settings; an Internal Access Manager may change their own business roles but not their protected role. Access Managers may assign business roles to themselves and other accounts; implemented permissions take effect with the assignment. The protected Internal Access Manager role can be granted or revoked through the owner-controlled terminal command; audited changes in Internal Settings require privileged authorization, and the last active Access Manager cannot be revoked. The Internal Admin role itself can only be granted or revoked through the owner-controlled terminal command, never through the portal UI or account API. Its role name is not shown in portal UI labels.

An internal user with the **Internal Access Manager** role opens **Internal Portal → Internal Settings** to create and manage internal-user-only accounts. Creation requires a display name, unique username, temporary password, position, and an active, unmapped Hubstaff member in the token's organization. The **AOC Members** picker toggle is enabled by default and limits the list to the configured AOC team; turning it off shows other active organization members as well. Set the server-only `HUBSTAFF_INTERNAL_TEAM_ID` to the Hubstaff team ID for **AOC members** in each environment; the team and its membership are verified live, not kept as a hardcoded user list. The picker also requires the server-only `HUBSTAFF_ACCESS_TOKEN` organization token. A missing or unverifiable team setting blocks the AOC-only filter, but the organization-wide mode can still show verified organization members. `GET /api/internal/hubstaff-members` is restricted to account creators and returns names and IDs only; `?aoc_only=false` selects organization-wide mode. The server checks active organization membership again when an account is created or its mapping is changed, so an unavailable or outside-organization member cannot be submitted by editing the browser request. Existing mappings remain reserved even when their portal accounts are inactive. Position applies default panels but does not grant a functional role. Managers can change identity, position, panels, Hubstaff mapping, and active state, except on their own account; they may manage business-role assignments on their own account and others. Placeholder role assignments take effect immediately for workspace panels, but grant no unimplemented business-data permissions.

Every active internal user with Account Settings enabled can update their own password under **Settings → Account security** using their current password. Other sessions are revoked. An Access Manager can reset another ordinary internal user's password in **Internal Settings** after re-entering their own current password. They cannot reset their own password or another protected manager/admin account. Internal Admin can reset another account, including protected accounts, but not themselves. The reset updates the credential hash, revokes the target's existing sessions, and records an audit event atomically. Share the new password through an approved secure channel; the portal does not display it again.

Changing the approved Hubstaff user ID clears the saved connection and requires reconnection. Pausing access clears credentials and invalidates in-flight synchronization; reactivation never restores old credentials. Management responses expose connection status, never ciphertext or tokens. Managers and Internal Admins cannot disable accounts holding either privileged role through this screen; revoke the Access Manager role or use the owner-controlled procedure for Internal Admin first. Account creation, updates, and role changes write audit events. Run `npm run internal-user:migrate` before deploying this cutover. The old administrator screen and API have been removed.

The Team directory shows active AOC Hubstaff members' names and derived work status to active internal users with the Team panel enabled. Members with portal accounts also show their saved portal position and a **Portal account** label; an unmapped member has no portal position. The server needs `HUBSTAFF_ACCESS_TOKEN` and `HUBSTAFF_INTERNAL_TEAM_ID` to verify the roster; if unavailable, it does not substitute a partial list of portal users. Team never includes another user's Hubstaff connection status, mapping ID, leave details, or account-management fields. Internal Access Managers and Internal Admins see connection status in Internal Settings instead. The status reader uses the organization token for approved Hubstaff leave and, after schedule coverage is verified, expected shifts; unverified status is **Unknown**. The shared Team page does not aggregate other users' personal tokens, return their tasks, or allow task assignment. Project Management separately reads shared organization projects and tasks from the Tasks PAT. Old saved `team_tasks` panel keys are ignored. Existing accounts with an explicit saved panel list missing `team_directory` have Team disabled until a manager turns it on; accounts without a saved panel list use their position's default panels.

## Development setup

To preview a panel locally without changing an account's roles, sign in as any active internal user and add an allow-listed `debug_panel` query parameter. For example, `/internal/team?debug_panel=team_directory` shows a sample directory, while `/internal?debug_panel=my_tasks` shows sample tasks. The preview requires `NODE_ENV=development` and a loopback host (`localhost`, `127.0.0.1`, or `[::1]`). It uses example records, never loads the real dashboard API, and does not save the preview daily plan. It does not enable a panel or grant real data access. The personal Hubstaff connection form is omitted. Remove the parameter to return to normal permissions. The preview banner links to the other available panel previews.

Confirm that `.env.local` targets the intended development database. Preserve its existing values, particularly `BETTER_AUTH_SECRET` and `HUBSTAFF_TOKEN_ENCRYPTION_KEY`.

```powershell
npm run internal-user:migrate -- --dry-run
npm run internal-user:migrate
npm run setup:check -- --internal-user
npm run internal-user:create -- USERNAME "DISPLAY NAME" APPROVED_HUBSTAFF_USER_ID
npm run internal-user:role -- grant USERNAME internal_access_manager
npm run dev
```

After migrating, bootstrap an Internal Admin or first Internal Access Manager before relying on account management in Internal Settings. The protected Access Manager role can be granted or revoked through the owner-controlled terminal command, which remains available for initial setup and recovery and cannot revoke the last active manager. Privileged changes through Internal Settings are audited. To grant Internal Admin access, run `npm run internal-user:role -- grant USERNAME internal_admin` after the migration. Access Managers can manage business roles on their own and other accounts in Internal Settings; no second approval is needed for implemented role permissions. Existing assignments gain newly implemented role permissions automatically, so review role holders before activating each live data integration. Existing Project Manager accounts are backfilled with `project_management` once, when the role table is created; later position changes do not alter roles. Replace uppercase arguments with approved account details. Never put passwords or tokens in command arguments, source, documentation, chat, or logs.

An internal user uses the normal `/login` page, then opens **Settings → Hubstaff → Connect with Hubstaff**. The OAuth flow requests `hubstaff:read` and `tasks:read` only, verifies the approved Hubstaff identity and Tasks access, and stores the returned tokens encrypted. The manual personal access token form remains available as a fallback for existing users. Both connection types renew access and persist a rotated refresh token. Organization tokens are not supported for personal My Work. Never paste a PAT into chat or a command line. A PAT bound to a DPoP key also requires signed DPoP requests and is not supported by this form. See [OAuth setup and rollout](INTERNAL_HUBSTAFF_OAUTH.md) for the required application, environment variables, and migration.

Better Auth creates the authentication account before the internal user mapping transaction. If mapping creation fails, the new login has no internal user/client/admin access. An administrator must inspect and recover that newly created account before retrying. The command never converts an existing account or changes its business permissions.

## Hubstaff reads and identity boundary

The server uses only these fixed provider endpoints:

| Endpoint | Purpose |
| --- | --- |
| `POST https://account.hubstaff.com/access_tokens` | Exchange the initial PAT and renew access with the current rotated refresh token |
| `GET https://api.hubstaff.com/v2/users/me` | Verify token ownership against the approved mapping on every connection/dashboard refresh |
| `GET https://api.hubstaff.com/v2/organizations` | List only organizations where the verified internal user is an active member |
| `GET https://api.hubstaff.com/v2/organizations/{id}/activities` | Read the verified internal user's activity blocks within exact configured-timezone boundaries for today and the current week |
| `GET https://tasks.hubstaff.com/api/v1/members/me` | Resolve the Tasks member ID used in assignments; it differs from the Hubstaff V2 user ID |
| `GET https://tasks.hubstaff.com/api/v1/projects` | Read projects accessible to that personal token |
| `GET https://tasks.hubstaff.com/api/v1/tasks/my/assigned` | Read assignments for the token's owner |

The mapping comes from the authenticated portal account, never the request. Tasks must also contain that Hubstaff user in `assignee_ids`, a consistent list identity, and a project present in the accessible-project result. Unexpected or unassigned records are excluded. Workflow labels come from each task's embedded list. Project filters/search/sort operate only on the already-authorized response in the browser.

The adapter follows bounded pagination (500 items per page, at most 10 pages per collection), uses a 45-second total deadline, and does not follow redirects or retry automatically. Weekly time reads are capped at ten accessible organizations and are always filtered to the already verified Hubstaff user ID. Today and week boundaries use the verified internal user's `time_zone` from Hubstaff `/v2/users/me` and are converted to exact instants before querying raw activity blocks; organization-local daily labels are not used because they can disagree with the internal user's reporting day. `HUBSTAFF_REPORT_TIME_ZONE` is only a fallback if Hubstaff omits or returns an invalid account timezone. Today AR and Weekly AR use Hubstaff's weighted activity formula: summed `overall` active seconds divided by summed `input_tracked` seconds. Time from sources without keyboard or mouse monitoring is excluded, and AR remains unavailable when there is no monitored input. If an organization plan or permission blocks activity reads, task data remains available and the UI marks time as unavailable or partial. Hubstaff may delay activity data, so the summary is not a live stopwatch.

A truncated collection displays an explicit incomplete-snapshot notice. Counts represent the loaded snapshot, not guaranteed lifetime totals. Tasks are returned only when their project is still in the accessible-project list and the Tasks API confirms the current Tasks member as an assignee. Task descriptions are sanitized to remove markup, external links, email addresses, and credential-like values before crossing the server boundary. Direct task links are constructed only from validated numeric organization, project, and task IDs. No comments, pay rates, raw user profiles, tokens, or other internal users' assignment data are returned. Recent activity uses task `updated_at`, not a comment feed. Due-soon means within three days; date-only deadlines run to the end of the viewer's local day.

Provider protocol origins are fixed constants, not environment-specific tenant URLs. No internal user, client, organization, or project IDs are hardcoded in application logic. This integration never uses the shared client Hubstaff token store or refresh path. Access tokens are reused until close to expiry, so Hubstaff's PAT exchange rate limit is not consumed on every dashboard refresh.

Official references: [current user](https://developer.hubstaff.com/reference/users/), [accessible projects](https://developer.hubstaff.com/tasks/reference/projects/), [my assigned tasks](https://developer.hubstaff.com/tasks/reference/tasks/), [access-token lifecycle](https://developer.hubstaff.com/authentication/).

## Credential handling

The password field is a server-rendered native HTML form. It posts directly to `/api/internal/connection`; frontend JavaScript does not read the value, put it into React state, or store it. As with any password form, the person entering the credential and their browser can inspect their own input and outgoing request. The server never embeds a saved token into markup, JavaScript, URLs, or responses.

The connection handler validates origin, session, active internal user access, exact form fields, and body size. It exchanges the PAT and confirms identity and Tasks API access before replacing a working connection. Only a fixed status code appears in the redirect URL. Use HTTPS outside loopback development. Request bodies and Authorization headers must remain excluded from infrastructure logging.

Tokens are encrypted using the existing AES-256-GCM helper with a derived key bound to both the portal user and approved Hubstaff identity. Moving a ciphertext to another internal user record cannot decrypt it. The root key stays in the existing server-only `HUBSTAFF_TOKEN_ENCRYPTION_KEY`; changing it requires reconnecting affected internal users and can affect the pre-existing client PAT store, so do not casually rotate it during setup. A database row lock serializes refreshes so concurrent requests do not reuse a rotated token.

Connection/refresh attempts have a 15-second cooldown enforced in PostgreSQL across server instances. A successful connection permits its initial dashboard refresh immediately, but cannot bypass the reconnect cooldown. Writes and synchronization completion compare the active flag, approved mapping, and connection version to reject stale operations after a connection change or deactivation. Responses use `private, no-store`; no shared or persistent task cache is used. The internal user layout keeps only the signed-in tab's already-loaded workspace responses in memory until the layout is unloaded, and an explicit header refresh replaces the personal workspace snapshot. Provider errors are converted to fixed friendly messages without forwarding response bodies or exception text.

## Files and verification

Internal user portal code is in `lib/internal-user-*`, `components/internal`, `app/internal`, and `app/api/internal`. Internal user administration uses the role-protected `/api/internal/internal-users` endpoint and `components/internal/internal-settings-controls.js`. Client controls, the existing client Hubstaff adapter, Python backend, ChatKit, and assistant logic remain unchanged.

```powershell
npm test
npm run test:internal-user
npm run test:internal-user:database
npm run test:internal-user:ui
npm run lint
npm run build
npm run test:internal-user:secrets
.venv\Scripts\python.exe -m unittest discover -s chatkit_backend/tests -v
```

The internal user unit/route tests use synthetic credentials and mocked provider responses. Actual Better Auth login and session verification run against an in-memory SQLite database using the application's auth configuration. PostgreSQL tests use temporary tables inside a rolled-back transaction, testing additive/idempotent schema, preserved legacy fixtures, unique mapping, encrypted isolation, rate limiting, stale writes, and revoked access. No model calls are made.

The browser suite runs the real internal user dashboard/form in a separate UI harness on port 3100 with synthetic task responses. It checks desktop/mobile layout, horizontal overflow, filters, loading/empty/error states, persistent workspace navigation, request reuse, shared-header refresh, and native token submission. It requires Google Chrome installed locally. Test screenshots are written to ignored `test-results/`.

With both local services running, an additional **development-only** authenticated test is available:

```powershell
npm run test:http
npm run test:internal-user:http -- --development-fixtures
```

The opt-in internal user HTTP test creates uniquely named client/admin/internal fixture accounts in the configured development database, logs in through the real HTTP API, checks routing and role denials, and exercises client Hubstaff's unconfigured state and signed ChatKit history. It removes only its own fixture records in `finally` and compares existing client, admin, membership, and ChatKit snapshots. Run it only against a confirmed development database with the local frontend origin; it is not a production health-check script. Interrupted processes may leave `smoke-` fixtures requiring exact-record cleanup.

Release verification still needs an approved real internal user account and current personal Hubstaff token, plus a preview smoke test of real client/admin workflows, connected client Hubstaff data, and an authorized AI reply. Synthetic/provider-mocked tests do not prove real token scopes, upstream account configuration, billing, or live production behavior. Do not deploy until those checks pass.

## Rollback

Keep this feature on its branch until reviewed. Stop local processes before switching application revisions. After this migration runs, an older application revision that still queries `portal_employees` is not schema-compatible. Reverting the application therefore requires a reviewed compatibility migration; do not recreate a second mapping table or copy account rows manually. Do not drop existing client, admin, auth, ChatKit, usage, or integration tables.

If internal user access must be retired, first disable the accounts, revoke their Better Auth sessions, clear saved tokens, and confirm that they have no client memberships or admin rows before changing the guards. Keep the mapping rows for audit/recovery. No production deployment, merge, or push is part of this implementation.
