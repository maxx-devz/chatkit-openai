# Phase 0 Internal Portal panel access checklist

This checklist covers **live Phase 0 access**, not future business dashboards. The [Navigation Page and Panel Matrix](PORTAL_NAVIGATION_PAGE_PANEL_MATRIX.md) also maps proposed workspaces and future fields. A visible panel never grants data permission by itself. The server checks the active internal-user account, assigned panel, effective permission, and record/field policy before returning data. Team is enabled by all four position presets, but can be toggled off per account. Use ordinary page URLs for manual checks; `debug_panel` is a local sample-data preview and is **not** an authorization test.

| Panel | Page / API | Allowed account | Denied or limited case | Live data boundary |
| --- | --- | --- | --- | --- |
| Overview | `/internal` / `GET /api/internal/dashboard?workspace=personal` | Active internal user with `overview` and `work.overview.read` | No personal panel or missing permission: API `403`; Overview-only must not receive task descriptions or links | Own Hubstaff summary and approved task-summary fields only |
| My tasks | Same page/API | Active internal user with `my_tasks` and `work.tasks.read` | No `my_tasks`: no full task details, even when Overview or Activity is visible | Verified user's own assigned tasks only |
| Activity | Same page/API | Active internal user with `activity` and `work.activity.read` | Activity-only response has no task description, project collection, or work summary | Own recent task-status fields only |
| Team directory and status | `/internal/team` / `GET /api/internal/dashboard?workspace=team` | Active internal user with `team_directory` panel and baseline `people.directory.read`; derived status requires `people.work_status.read` | Team toggled off or missing from saved panel list: API `403` and no sidebar link; inactive or unauthenticated accounts also denied. Unverifiable AOC roster: API `503`, not a partial portal-only list | Active AOC Hubstaff team members' names, optional mapped portal position, mapping label, and derived status only; no colleague connection, Hubstaff ID, leave reason, or dates |
| HR workspace | `/internal/roles/hr` / `GET /api/internal/hr?month=YYYY-MM` | Active internal user assigned HR or Internal Admin, with HR read permissions and at least one enabled HR panel | Neither role or no HR panel: API `403`; malformed month: `400`; source failure: `503` and no partial data. Disabled sections are omitted from the API response. | Active AOC members only: approved leave calendar; separately toggled request details, annual policy balances, schedule records, and summary counts; no pay or raw activity |
| Project Management projects and tasks | `/internal/roles/project_management` / `GET /api/internal/project-management[?project_id=ID]` | Project Management role or Internal Admin with `work.projects.read` and an enabled PM panel; task requests also require `work.team_tasks.read` and `pm_project_tasks` | Missing role or panel: `403`; invalid ID: `400`; project outside verified catalog: `404`; provider failure: `503`; no task write endpoint | Shared accessible AOC Hubstaff Tasks organization: folder and active project names; selected project's whitelisted task fields only. Personal My Work remains self-only |
| Personal Settings password change | `/internal/settings` / `POST /api/internal/password` | Active internal user with `account_settings` panel and self-only `account.password.change` | Disabled panel, unauthenticated or inactive account, or wrong current password: denied; other sessions revoked on success | Own login only; no password returned |
| Hubstaff settings | `/internal/settings` / `GET /api/internal/dashboard?workspace=settings`; `POST /api/internal/connection` | Active internal user with `hubstaff` and the relevant `hubstaff.connection.read`/`.manage` permission | No panel: Hubstaff connection UI and data are hidden and mutation refused; Settings remains available only if Account Settings is enabled | Own approved Hubstaff mapping and connection status; never saved token fields |
| Internal Settings → Users & Access | `/internal/internal-settings` / `GET/POST/PATCH/PUT /api/internal/internal-users`; `PUT /api/internal/password` | Internal Access Manager or Internal Admin with the action-specific permission | Ordinary or planned-only role: API `403`; Access Managers cannot reset privileged accounts; self-reset denied | Internal accounts and effective permissions; audited changes and password resets; no credential ciphertext |
| Internal Settings → Integrations | `/internal/internal-settings/integrations` / `GET/POST /api/internal/integration-settings` | Access Manager or Internal Admin may read; only Internal Admin may run a manual Hubstaff connection test | Ordinary role: API `403`; Access Manager test: `403`; untrusted POST origin: `403`; missing audit migration: test `503` | Server-side configuration presence, non-secret AOC team ID, and safe test status only; no tokens or member names |
| Internal Settings → Sync | `/internal/internal-settings/sync` / `GET/PUT /api/internal/sync-settings` | Access Manager or Internal Admin may read; only Internal Admin may change intervals | Ordinary role: API `403`; Access Manager interval edit: `403` | Per-feed read-through freshness intervals and last cached time; no background schedule |
| Audit Log | `/internal/audit` / `GET /api/internal/audit` | Internal Access Manager or Internal Admin with `platform.audit.read` | Ordinary or planned-only role: API `403`; direct URL cannot bypass the permission check | Recent safe integration-run fields, panel/role read actions, and account changes; no source payloads or credentials |
| Other My Workspace role panels | `/internal/roles/{role}`; `/internal/roles` redirects to the first available role | Active internal user assigned that business role; Internal Admin may view all Phase 0 panels | Unassigned, unknown, and protected administrative role URLs have no panel content | Static placeholder text only; no business API requests or live data |

The shared live-panel policy in `lib/internal-panel-access.js` drives navigation, page entry, and dashboard API gates. Individual dashboard response fields still use panel-specific checks. HR has five independently toggleable panels; Project Management has separate Projects and Project Tasks panels. If all panels for either role are off, that role's navigation link disappears and its API denies access. A disabled PM task panel removes its sidebar child and blocks `project_id` task requests. New role panels should follow this same panel registry, default/backfill, server gate, and field-projection pattern. Internal Admin's explicit allow-list includes them all. Other role panels are static placeholders.

Integration Settings is an administrative section within Internal Settings, not a per-user dashboard panel. Hubstaff is the only active connection shown. HubSpot, Help Scout, Google Drive, and Make are labeled Planned without probing or claiming a working connector. The Hubstaff test validates the organization token and configured AOC team through a read-only provider call; it is not a background sync or proof of future token validity. Credential values and personal Hubstaff tokens remain outside this UI. The separate Integration & Sync section controls read-through cache freshness in minutes, not a scheduled worker. Non-secret configuration is currently deployment-managed; editable database-backed options require a later explicit design and migration.

The Internal Settings sidebar group expands to Users & Access, Integrations, and Sync on desktop and in the mobile drawer; Audit Log remains a separate link. These three administrative children use the management role permission, not a per-user panel toggle. Future panel-backed children must pass both the saved panel toggle and live permission before appearing. A hidden child never substitutes for page and API authorization.

## Project Management workspace release checks

The PM foundation is read-only and locally verified. Before production use, confirm the server-side Tasks PAT can see every intended AOC folder, active project, and member; a PAT tied to one Hubstaff user is not proof of organization-wide coverage. If multiple Tasks organizations become accessible, configure `HUBSTAFF_TASKS_ORGANIZATION_ID` to the approved one. Review all existing Project Management and Internal Admin role holders because these permissions become live with deployment.

- Check that users without the role or with both PM panels off receive API `403`, even by direct URL. Turning off only Project Tasks must remove its sidebar child and reject `project_id` requests.
- Check that an arbitrary or foreign project ID cannot return tasks. The catalog verifies project membership before a task read, and each returned task must belong to that project.
- Confirm titles, stages, status, assignees, and due dates against Hubstaff Tasks. Descriptions, comments, credentials, time reports, and write actions must remain absent.
- Verify the separate 60-minute catalog and 5-minute selected-project task intervals in Internal Settings; manual refresh is still subject to the one-minute cooldown. Confirm provider reads and panel reads appear in Audit Log.
- The source reader caps a project's task read at 1,000 records and marks the response partial when more remain. A full organization-wide completeness check and authenticated staging account test remain pending.

## HR workspace release checks

The read-only HR panel is implemented locally, but the intended deployment and existing HR and Internal Admin role holders must be reviewed before release. Granting either role activates the HR permissions immediately; an HR Admin position alone does not grant them.

- The API filters Hubstaff organization records to the configured active AOC team before returning them. Pagination or source failure must return no partial HR response. Raw Hubstaff IDs, pay, screenshots, activity metrics, and provider payloads are excluded.
- Leave request dates, policy, status, reason, and per-day hours; annual per-policy balances; and schedule records are restricted to HR and Internal Admin. Team retains only its derived status.
- The calendar includes approved requests only; submitted and denied requests stay in the separately toggleable request list. Balances show each employee once with all policy balances. Requests, balances, and schedule-record lists support 10/20/50-row pages and sorting. The schedule view reports records on file and members needing review, not live attendance or guaranteed staffing coverage.
- The page is read-only: no approval, balance adjustment, policy edit, or schedule write endpoint exists. Those actions remain in Hubstaff.
- Validate approved/submitted/denied request behavior, partial days, year boundaries, negative balances, archived policy names, and schedule coverage against the intended deployment. HR data owner approval of retention and field policy remains pending.
- The local organization token returned an AOC-scoped current-month view for 18 members, 19 requests, 69 balance rows, and schedule records for 17 members on 2026-10-15. This is a source-path check, not a production authorization or data-quality signoff.

## Team work status release checks

The derived-status reader and server-side field filter are implemented, with unit and API fixture tests. The [field policy](PORTAL_NAVIGATION_PAGE_PANEL_MATRIX.md#team-work-status-policy) permits only **On Shift**, **Off Shift**, **Away**, or **Unknown** in the shared directory. Detailed leave dates and reasons remain restricted to HR and Internal Admin. Verify the organization token and schedule coverage in the intended deployment before enabling shift labels with `HUBSTAFF_TEAM_SCHEDULES_VERIFIED=true`.

- An active user with Team enabled, `people.directory.read`, and `people.work_status.read` may receive only the derived status for each active AOC Hubstaff team member, including members without portal accounts. Without the panel or either permission, direct API calls must not return it. The mapping label is not a Hubstaff connection indicator.
- The roster requires the organization token and configured AOC team ID. If membership cannot be verified, the request fails without substituting active portal accounts.
- A fresh, complete organization read with approved leave at the member's current local time yields **Away**, even during a scheduled shift. Future, pending, denied, and non-overlapping partial-day requests must not yield **Away**.
- With no current approved leave, a verified expected shift covering now yields **On Shift**; a verified, complete schedule explicitly showing no shift now yields **Off Shift**. An absent schedule must not yield **Off Shift**.
- Incomplete or stale leave reads and unknown request states yield **Unknown**; a portal-account mapping is not required for status. A missing member timezone prevents shift labels, but a confirmed approved leave interval with an explicit offset can still yield **Away**. Otherwise missing, failed, or stale schedule coverage yields **Unknown**, never a false On Shift or Off Shift.
- The Team response must never include raw schedules, leave category, reason, request ID, start or end date, balance, approver, or raw Hubstaff payload. Internal Admin sees HR leave details only through the separately authorized HR reader.
- The local organization token read 18 schedule records for 17 of 31 Hubstaff members in a 2026-10-07 through 2026-10-21 check. The scheduled members are expected to cover Team. A read-only comparison against the database configured in `.env.local` found two active internal portal accounts; both approved Hubstaff IDs appeared in the organization member list and the schedule results. The other 15 scheduled members had no active portal account in that database. Recheck mapping as the portal roster expands and verify that schedules represent the team's actual expected shifts.
- Check the deployed organization token's cross-member leave and schedule access separately from the successful local checks, then exercise allowed and denied cases with non-production accounts before enabling shift labels. Failed reads currently appear as **Unknown** and an integration-run audit failure; manager/admin notification delivery remains a separate task.

On 2026-10-15, a read-only smoke check using the development database's four active Hubstaff mappings completed the organization reader for all four. The check printed no identities or status values. This confirms the current token and API query path locally, not the future Vercel project's credentials or schedule authority.

## Automated checks

- `npm run test:internal-user` covers allowed/denied panel and workspace combinations, role-panel visibility, API response-field filtering, derived Team status and its private-field boundary, incomplete Hubstaff reads, planned-role denial, account-management actions, and cross-account Hubstaff isolation.
- `npm run test:internal-user:ui` covers responsive My Work, Team status badges on desktop and mobile, Settings, direct role-panel sidebar links/mobile drawer, and the Internal Settings role/permission display with fixture data. It does not substitute for real authentication or database authorization testing.
- `npm run lint` and `npm run build` check integration and compilation.
